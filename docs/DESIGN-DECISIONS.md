# Устройство и принятые решения

Документ описывает технические решения прототипа, их назначение и ограничения.

## 1. Отдельное Windows-приложение

Выбраны **C# / .NET 10 / Windows Forms**: они дают обычный Windows-интерфейс,
доступ к захвату экрана и глобальным горячим клавишам, а также позволяют
опубликовать приложение вместе с .NET Runtime.

Целевой процесс — x64. Нативные библиотеки OCR также берутся из папки `x64`.
Публикация многофайловая: Tesseract загружает нативные DLL, а языковые модели
должны находиться в доступном каталоге `tessdata` рядом с программой.

Для `dist` это устройство сохранено. Однофайловый релиз 0.2.0 дополнительно
использует профиль `Properties/PublishProfiles/SingleFile.pubxml`: self-contained,
без trimming, с компрессией, включением нативных библиотек и извлечением всего
содержимого до `Main`. Режим совместимости .NET 10 сохраняет реальные пути и
исходную структуру `x64` / `tessdata` / `licenses` в приватном временном кэше;
менять алгоритм OCR и пути в OcrReader не потребовалось. Нативный CoreCLR
в однофайловом host встроен в EXE, отдельный `coreclr.dll` не требуется.
Пользовательская история остаётся вне кэша. Выпуск собирается отдельным
`tools/build-release.ps1`, не заменяющим работающий `dist`. При смене SDK режим
полного извлечения и Tesseract нужно заново проверять: это режим совместимости,
а не рекомендуемый универсальный вариант для любых будущих .NET-приложений.

`Core` содержит платформенно-независимые решения; `Windows` — UI, GDI и OCR.
Это позволяет проверять правила подсчёта без запуска Fortnite или Windows GUI.

## 2. Распознавание экранного уведомления

Схема обработки:

```text
Выбранная область экрана
  → ScreenCapture
  → OcrReader: подготовка изображения + Tesseract
  → строки с координатами и уверенностью
  → NotificationClassifier
  → NotificationGate
  → CounterLedger
  → окно и оверлей
```

Небольшая область вокруг XP уменьшает нагрузку и помогает отделить уведомление
от заданий, чата и подсказок. Координаты сохраняются в физических пикселях,
включая отрицательные координаты монитора слева от основного.

По умолчанию сканирование выполняется только при активном окне с `Fortnite`
в заголовке и процессом `FortniteClient-Win64-Shipping*` / `Fortnite`.
В 0.1.2 проверка процесса закрывает ложное совпадение заголовка OpenCode.
Собственные окна программы исключаются по PID. Переключение
на другое окно разрывает последовательность наблюдений.

GDI-захват и отдельный оверлей рассчитаны на **оконный режим без рамки**.
После изменения разрешения или положения игры область нужно выбирать заново.

В исправленном `ScreenCapture` используется прямой `BitBlt` с растровой операцией
`SRCCOPY | CAPTUREBLT` (0x40CC0020), чтобы сохранить захват слоистых окон.
`Graphics.CopyFromScreen` проверяет значение перечисления и отвергает такое
сочетание флагов: этот дефект исходной 0.1.0 воспроизведён на Windows и блокировал
выбор области. DC рабочего стола получается через `GetDC(NULL)`, DC картинки —
через `Graphics.GetHdc`; оба освобождаются в `finally`, включая путь ошибки.
Ошибка `BitBlt` передаётся как `Win32Exception`, не затрагивая статистику.
Статус публикации исправления и ограничения проверки описаны в `VERIFICATION.md`.

## 3. OCR и подготовка картинки

- Движок: NuGet `Tesseract` **5.2.0**, режим `LstmOnly`.
- Модели: `tessdata_fast`, языки `eng`, `rus`, по умолчанию `rus+eng`.
- Ревизия моделей: `87416418657359cb625c412a48b6e1d6d41c29bd`.
- Картинка увеличивается в **2 раза**, по краям добавляется **16 пикселей**.
- Используются `PageSegMode.SparseText` и заданный DPI 200. В 0.1.2, если
  уведомление не прошло Core-проверку, выполняется SingleBlock того же кадра.
- Положение распознанных строк переводится обратно в пиксели исходной области.

Фильтр делает яркие буквы чёрными на белом фоне. Текущие RGB-условия:

| Цвет | Условие |
| --- | --- |
| Белый | max(R,G,B) ≥ 170, min(R,G,B) ≥ 120, разница ≤ 80 |
| Жёлтый / золотой | R ≥ 175, G ≥ 145, B ≤ 160 |
| Фиолетовый | B ≥ 185, R ≥ 135, G ≥ 90 |

Это начальные пороги, а не калибровка по реальным кадрам пользователя.
Фильтр можно отключить: тогда OCR получает увеличенное исходное изображение.
Порогами и масштабом управляет `OcrReader.cs`.

## 4. Как текст признаётся открытым сундуком

`NotificationClassifier` ищет отдельное слово `CHEST` или `СУНДУК`.
Границы слова не дают принять `CHESTS`, `СУНДУКИ` или `CHESTPLATE` за уведомление.
На той же строке исключаются некоторые формулировки заданий и взаимодействия.

Уверенность строки с сундуком должна быть не ниже **40%**. По умолчанию
требуется XP рядом; для вспомогательных строк допускается уверенность **20%**.

Для строк XP проверяется расстояние между центрами:

- по X: не больше `max(140, ширина_строки_сундука × 1.8)`;
- по Y: не больше `max(64, высота_строки_сундука × 4)`.

Распознаются обозначения `XP`, похожие кириллические `ХР` / смешанные буквы,
а также `ОП`, `ОПЫТ`, `ОПЫТА`. В соседнем тексте требуется `+` с цифрой или
число перед обозначением XP. Само количество XP не переводится в число сундуков.

Расширять словарь и ослаблять условия стоит по подтверждённым кадрам:
случайное слово в списке заданий не должно увеличивать счётчик.

### Поправка ОП по реальному кадру, версия 0.1.1

На `assets/samples/chest-01.png` подпись СУНДУК распознаётся с 96%, но соседнее
`+1 200 ОП` — как `+1 2000n` или `+1 2000п`. Исходная проверка XP отвергала
уведомление. Сравнение языка, масштаба 2×/3×/4×, фильтра и PSM показало, что
изменение подготовки изображения не решало обе проверки надёжнее.

Добавлена отдельная проверка `AmbiguousRussianAward`: ошибка формы
`(О/O/0)(П/N)` принимается **только** при отдельном русском слове СУНДУК и
явном `+число` непосредственно перед единицей **на той же строке**. Между
буквами единицы не допускается пробел, после неё — буквы или цифры. Это не
расширение общего `XpWord`: отдельное `0n`, разнесённые `+1200` / `0n`,
английский CHEST и задания не дают такого зачёта. Вариант `доп` не добавлен.

Прежние границы расстояния и уверенности сохранены; сумма XP не вычисляется.
Сырой текст в поле диагностики не исправляется и может всё ещё содержать `2000n`.
Фильтр RGB, масштаб, SparseText, модели и параметры `NotificationGate` не менялись.
Добавлены положительные и отрицательные тесты, включая геометрию реального кадра
  и смену написания ОП без повторного зачёта.

### Запасной OCR-проход, версия 0.1.2

В живых кадрах SparseText игнорировал подпись СУНДУК, хотя она присутствовала
в исходнике и маске. SingleBlock восстанавливает две строки. `ReadNotification`
готовит картинку один раз и проверяет по очереди полные результаты двух PSM
через тот же `NotificationClassifier` с пользовательским `RequireXp`.
Удачный результат возвращается целиком; XP и название не собираются из разных
проходов. Если оба результата не подходят, возвращается исходный SparseText
для диагностики. Один кадр даёт одно наблюдение gate; пороги не снижены.
Это запасной проход, а не замена SparseText: исходный PNG лучше читался первым
режимом, а некоторые живые кадры — вторым. Неудачные кадры требуют больше CPU,
но сканирование остаётся последовательным с прежним интервалом.

## 5. Защита от повторов и быстрые открытия, версия 0.3.1

`NotificationGate` получает от OCR три сигнала:

- `visible` — в кадре всё ещё есть слово `СУНДУК` / `CHEST`, даже если строка XP
  не прочиталась;
- `signature` — распознанное уведомление целиком либо `null`;
- монотонное время `Stopwatch`.

Подпись строится из канонического слова `СУНДУК` / `CHEST` и центра строки.
Две подписи совпадают, если центр отличается не больше чем на 12 px по каждой оси:
дрожание OCR на несколько пикселей не должно менять подпись (жёсткая сетка 24 px
такой сдвиг превращала в смену подписи и сбрасывала подтверждения). Сдвиг строки HUD
на целый ряд (около 24 px) по-прежнему даёт новую подпись.
Сумма XP в подпись не входит: OCR путает `200` и `2000n`,
а одинаковые награды не должны создавать новое событие. Положение входит,
потому что новая строка HUD обычно сдвигает соседние.

| Параметр | Сейчас |
| --- | --- |
| Подтверждения первого появления | 2 |
| Подтверждения уведомления с другой подписью | 3 |
| Отсутствие для повторного зачёта | 200 мс и 2 пропущенных сканирования |
| Минимальный интервал между зачётами | 700 мс |

После зачёта событие блокируется. Если подпись меняется, новая строка должна
подтвердиться три раза: одиночное мигание OCR не создаёт второй сундук. Если
подпись та же, блокировка снимается только после короткого устойчивого отсутствия.
`visible` не даёт считать пропавшую строку XP исчезновением всего уведомления.

Короткое отсутствие в 200 мс нужно для двух уведомлений, которые сменяют друг
друга с паузой на анимацию. Прежние 900 мс и 1400 мс не успевали снять блокировку
между быстрыми открытиями. Пауза и потеря фокуса сами по себе не доказывают
исчезновение: `BreakObservationSequence` сбрасывает подтверждения и таймер
отсутствия, сохраняя блокировку.

Ручная поправка и новый матч вызывают `SuppressUntilClear`, чтобы видимое
сообщение не было автоматически засчитано сразу после ручного действия.
Подавление действует и на уведомление с другой подписью.

Остаточное ограничение: если игра заменяет уведомление другим с тем же текстом
в той же точке без заметного исчезновения или сдвига, отличить его от одной
длинной надписи по одному кадру нельзя. Это нужно проверять на реальной записи
двух быстрых открытий; обещать полное решение без таких кадров нельзя.

## 6. Статистика и сохранение

`CounterLedger` хранит список событий: ID, ID матча, время, локальную дату,
источник `automatic` / `manual`. Счётчики вычисляются из этого списка:

- матч — события с текущим ID матча;
- сегодня — события с сохранённой датой текущего дня;
- всего — число оставшихся событий.

Новый матч создаёт новый ID. `−1` удаляет последнее событие текущего матча
и корректирует именно дату этого события. Поэтому отмена после полуночи
не уменьшает ошибочно статистику нового дня.

`JsonFile` записывает `.tmp`, сбрасывает данные на диск и заменяет основной
файл. Состояние в памяти меняется после успешной записи. Повреждённый JSON
останавливает загрузку с сообщением об ошибке и сохраняет исходный файл.

Данные лежат в `%LOCALAPPDATA%\FortniteChestCounter`, схема имеет версию 1.

### Дневная статистика, версия 0.2.0

`CounterLedger.DailyCounts(from, through)` возвращает упорядоченный ряд
`DailyChestCount` для каждого дня включительного периода, включая нули.
Группируется сохранённое поле `Day`, а не `Timestamp`, повторно переведённый
в текущую временную зону: дата события не должна меняться после смены часового пояса.
Учитываются все матчи и оба источника; отменённые события уже удалены из журнала.
`FirstRecordedDay` задаёт начало периода «Всё время». Чтение не записывает файлы
и не меняет текущий матч; схема 1 и пользовательские настройки остаются прежними.

`StatisticsForm` — одно немодальное дочернее окно главного окна. Доступны
7 / 30 дней, текущий месяц, вся история и произвольные даты. Встроенные периоды
включают сегодня; в своём периоде обе границы включительны. При неверном порядке
дат старый график очищается и показывается пояснение. Главное окно обновляет
статистику при изменении общего числа событий или наступлении нового дня,
а не пересчитывает длинный ряд на каждом OCR-кадре. Новые зачёты и отмены
сохраняют позицию прокрутки; смена периода возвращает её к началу.

`DailyChartControl` отрисовывает столбцы через GDI+ без новых зависимостей.
Короткий период заполняет доступную ширину; длинный получает горизонтальную
прокрутку. Рисуются только видимые дни, включая подписи года и точные подсказки.
Ось количества использует целые деления, нулевой день не рисуется положительным
столбцом. Размеры отрисовки учитывают DPI; перерисовка двойная буферизированная,
кисти, перья и ToolTip освобождаются. Окно исключается из захвата так же, как MainForm.
Открытие графика не меняет gate или параметры OCR; ограничение активным Fortnite
действует обычным образом при переключении на любое окно статистики.

## 7. UI и оверлей

OCR выполняется в фоновом `Task`, результаты передаются в UI через `Progress`.
Идентификатор запуска отбрасывает результаты старого цикла после паузы или
повторного выбора области. Окно и статистика обновляются на UI-потоке.

Оверлей — отдельное верхнее окно без активации, прозрачное для кликов.
Для пользовательской отрисовки шрифты заданы в пикселях, а координаты
масштабируются по DPI. Это помогает избежать двойного увеличения шрифта.

Окнам задаётся `SetWindowDisplayAffinity`, чтобы собственный UI не мешал захвату.
Регистрация горячих клавиш выполнена через `RegisterHotKey`; результат
регистрации показывается пользователю. Закрытие окна сначала завершает OCR.

### Настраиваемая клавиша «+1», версия 0.3.0

`HotkeyBinding` хранит Win32-модификаторы и виртуальный код клавиши в Core,
без зависимости от Windows Forms. По умолчанию остаётся `Ctrl+Alt+F9`, поэтому
старые настройки и привычное управление не меняются. В `settings.json` появилось
вложенное поле `addChestHotkey`; если его нет, десериализатор оставляет значение
по умолчанию. Некорректное ручное значение останавливает запуск с понятным
сообщением, как и другие неверные настройки.

Кнопка захвата перехватывает обычные клавиши, F-клавиши, стрелки, Tab и Enter;
`Esc` отменяет, одиночный модификатор игнорируется. WinForms не отдаёт Win как
модификатор, поэтому через интерфейс назначаются сочетания с Ctrl / Alt / Shift;
Win можно указать только вручную в JSON. Регистрация идёт с `MOD_NOREPEAT`.
Фиксированные `Ctrl+Alt+F7/F8/F10/F11/F12` зарезервированы. Сочетание без
модификатора разрешено после предупреждения, поскольку оно перехватывается
во всех программах. При занятом сочетании или ошибке сохранения возвращается
прежняя клавиша; настройка сохраняется только после успешной регистрации.

## 8. Переносимый комплект разработки

В исходной папке собраны код, модели, NuGet-пакеты восстановленной сборки,
готовая программа и эта документация. `NuGet.Config` направляет пакетный кеш
в `.packages` внутри проекта и даёт локальный источник `assets/nuget`.

PowerShell-скрипты используют расположение самой папки проекта, поэтому
Linux-путь `/home/cpet/...` не нужен для Windows-сборки. Конкретные шаги
находятся в `WINDOWS-DEVELOPMENT.md`.
